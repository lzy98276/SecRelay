# M0 探针实测记录

> 记录**我们自己的机器上**测出来的数字。所有结论都可以用仓库里的命令复现。
> 目的不是"证明性能好"，而是把设计文档里的假设换成实测值 —— 假设会错，数字不会。

---

## 记录 1：Windows 屏幕采集（DXGI Desktop Duplication）

**日期**：2026-10-06
**命令**：`target\release\secrelay.exe capture --seconds 5`
**环境**：Windows，显示 2560x1600，BGRA8，采集源为整屏桌面复制

| 指标 | 第 1 次（桌面近乎静止） | 第 2 次（终端持续打印） |
|---|---|---|
| 采集分辨率 | 2560x1600 | 2560x1600 |
| **实测帧率（release）** | **113.8 fps** | **104.5 fps** |
| 帧间隔 p50 | 8.69 ms | 9.18 ms |
| 帧间隔 p95 | 11.11 ms | 12.58 ms |
| 帧间隔 max | 14.43 ms | 19.88 ms |
| 单帧未压缩大小 | 15.62 MB | 15.62 MB |
| 累计原始数据速率 | 14.9 Gbps | 13.7 Gbps |
| 相邻帧变化比例（平均） | **0.02%** | **0.54%** |
| 相邻帧变化比例（最大） | 0.10% | **31.11%** |
| 理论收益上限（按平均） | 约 4000× | 约 187× |

### 结论

1. **采集不是瓶颈。** 两次实测的中位帧间隔都在 9ms 上下，已经包含
   「GPU 复制 → CPU 映射 → 逐行压平 → 整帧差分」的全部开销，60fps 的 16.7ms 预算有富余。
   > 这个数字还包含**两次拷贝**。将来改成"纹理直接交给硬编"（零拷贝）只会更快。

2. **不压缩根本不可行，这坐实了编码是必需品。** 2560x1600x4 = 15.62 MB/帧，
   60fps 就是 **937 MB/s ≈ 7.5 Gbps**。任何网络都扛不住，编码没有讨论余地。

3. **脏矩形差分的收益高度依赖画面内容，两次实测差了 20 倍。**
   两次唯一的区别是**屏幕上在不在动**：第 1 次桌面近乎静止（0.02%），
   第 2 次终端在持续打印文字（平均 0.54%，**峰值 31.11%**）。

   **这条修正了只看第 1 次数据会得出的结论。** 不能对外说"收益 4000 倍"——
   那个数字来自几乎不动的桌面，是**收益上限**。真实使用场景是两者混合：
   阅读/浏览时收益极高，打字、滚动、播放视频时收益迅速塌陷。

   对设计的直接影响：

   - 脏矩形差分**仍然值得做**（平均收益 187×~4000×，远超换编解码器的 1.5~2×），
     但它**必须有兜底路径**：检测到变化率超过阈值时退回整帧编码，否则
     "只传变化区域"在爆发场景下会产生大量碎片矩形，反而比整帧更差。
   - 需要**区域分类**（需求分析 §6.3 提到的"区域分类混合编码"）：
     静态文本区域走准无损、运动区域走普通视频编码，而不是一套参数通吃。
   - 峰值 31% 说明**"整帧变化"是真实存在的工况**，不是理论担忧。

### 必须说明的偏差

- 两次实测都是**开发机上的特定内容**，不是统计意义上的典型值。要得到可靠结论，
  应该按场景分类采样（纯阅读 / 打字 / 滚动 / 视频播放 / 全屏动画），每类单独记录。
- 差分度量的是**变化像素的比例**，不是**脏矩形面积**。真实实现按图块合并矩形，
  面积通常大于像素比例，所以实际收益会低于上面的数字。
- 采集**未合成鼠标指针**。DXGI 把指针形状单独给（`DXGI_OUTDUPL_POINTER_SHAPE_INFO`），
  远程桌面要显示指针就必须额外处理 —— 目前没做。
- 帧率两次差了 9%（113.8 vs 104.5），是系统负载波动，不是实现差异。

### 下一步要量的（尚未验证）

| 项 | 为什么重要 |
|---|---|
| 编码延迟与码率 | 采集不是瓶颈，编码大概率是。H.264 硬编 1080p60 的端到端延迟要实测 |
| 脏矩形实现的真实收益 | 从"0.02% 像素变化"到"实际省下多少码率"，中间隔着图块合并与矩形编码 |
| 文字可读性的最低码率 | 目标：1080p 静态文档 ≤2 Mbps 时 OCR 准确率 >99%（`docs/需求分析.md` §7） |
| 鼠标指针合成 | 不合成指针的远程桌面是不可用的 |

## 记录 2：一个踩过的坑（值得写下来）

**现象**：用 DXGI Desktop Duplication 抓屏，`AcquireNextFrame` 成功，但随后
`IDXGISurface::Map` 直接失败：

```
平台采集失败：映射复制表面失败：参数错误。 (0x80070057)
```

**原因**：`AcquireNextFrame` 返回的 `IDXGIResource` 是 GPU 上的复制表面，
**没有 CPU 访问权限**，不能直接 Map。这不是 API 用错参数，是设计如此。

**正确做法**：先 `ID3D11DeviceContext::CopyResource` 到一张
`D3D11_USAGE_STAGING` + `D3D11_CPU_ACCESS_READ` 的纹理，再 Map 那张。
该纹理在采集源构造时创建一次、每帧复用。见 `crates/secrelay-media/src/windows_dxgi.rs`。

## 记录 3：一个方法论教训

同一个采集探针，**debug 构建 11.6 fps，release 构建 113.8 fps** —— 差 10 倍。

原因是 release 之前，整帧逐像素差分（4.1M 像素 × 每帧）在无优化下耗掉了绝大部分时间。

**教训：任何性能数字必须标注构建类型。** 用 debug 构建的数据讨论"能不能跑到 60fps"
会得出完全错误的结论。本文件里的数字除特别说明外都是 release 构建。

## 复现方式

```bash
# 真实屏幕采集（Windows）
cargo build --release -p secrelay-cli
target\release\secrelay.exe capture --seconds 5

# 合成画面源（任何平台都能跑，不需要显示器）
cargo run --release -p secrelay-cli -- capture --synthetic --seconds 5

# 协议与会话模型自检
cargo run --release -p secrelay-cli -- selftest
```

> 提示：`capture --synthetic` 的图案刻意包含**小范围移动方块**与**底部状态条**，
> 所以它的变化比例是已知且可控的 —— 适合用来验证将来的脏矩形实现是否正确，
> 而不是用来估收益。
