# SecRelay 需求分析（v0.3 讨论稿）

> 定位语：**跨设备连接，让看、传、说归于一处**
> 目标平台：Windows / Ubuntu·Debian(Linux) / macOS / Android + **Web 客户端**
> 技术底座意向：Rust 核心 + 可替换的跨平台 UI
> v0.3 变更：**按已拍板决策重写范围**——砍掉 iOS 原生版、新增 Web 客户端。

本文档只做需求与可行性分析，不做实现。文末列出必须拍板的决策点。

> ⚠️ **方向调整（本阶段）：不做屏幕分享 / 远程看屏，也不做投屏。**
> 下文与屏幕采集、投屏相关的内容（FR-2、FR-5、§4 平台能力矩阵、§6.3 的脏矩形与编码论证、
> §9 里"看桌面"的切片等）一律按 **本阶段不做，依据留档** 理解 ——
> 保留是因为授权流程、硬编覆盖、零拷贝、平台差异这些论证对**摄像头**这一路同样成立，
> 但它们**不再是当前需求**，正文里"要做"的口吻请以本节为准。
> 当前范围：设备连接、摄像头、文件、文字与语音、Web 客户端。

## 0. 已锁定的决策（v0.3）

| # | 决策 | 影响 |
|---|---|---|
| ✅ 1 | **不做 iOS 原生版，改用 Web 客户端** | 原生平台从 5 个减为 **4 个**（Windows / Linux / macOS / Android）；**iPhone/iPad 用户经 Safari 接入**（iOS 16.4+ 可当完整观看端+文件端+语音端） |
| ✅ 2 | **不做远程控制，也不做屏幕分享 / 远程看屏** | 砍掉 FR-11 输入注入与整条屏幕采集—编码—显示管线（FR-2、FR-5）；"看"只保留摄像头；频道模型仍预留 `control` 位置 |
| ✅ 3 | **"传递话语"三类全要**：文字消息 + 语音消息 + 实时语音对讲 | 实时对讲（回声消除/降噪/抖动缓冲）是**独立子系统**，需单独立项排期 |
| ✅ 4 | **UI 框架由 M0 探针实测后决定** | 先不锁 Slint / Flutter，用"显示 1080p60 视频"的 demo 做判据 |
| ✅ 5 | **Web 端要做到"原生有的尽量有"** | Web 成为**第四个 UI 目标**；WebRTC 从"可选"变为**硬约束** |
| ✅ 6 | **连接以 P2P 为默认路径** | 媒体与实时数据走设备直连；服务器只做信令、中继兜底、离线消息暂存 |
| ✅ 7 | 打洞失败**允许中继兜底**（P2P 优先） | 中继只转发密文、服务器不解密；**"中继占比 <15%" 成为核心 KPI** |
| ✅ 8 | 消息**要求异步可达**，接受服务器暂存 | 需要**双棘轮（vodozemac）**保障暂存密文的前向安全，并运营一个**零知识的消息后端**；原则从"服务器不承载用户数据"修正为**"服务器零知识"** |
| ✅ 9 | 文件通道：**原生↔原生单独走 QUIC P2P**；Web 参与时走 WebRTC DataChannel | 需要**第二条 P2P 路径**（独立打洞/保活），工作量已计入 M1，见 §6.3 |

> **两个决策带来的意外收益**：
> 1. **砍掉 iOS 原生，等于顺手解决了最大的法务风险**——GPLv3 与 App Store 的冲突（VLC 下架案）直接消失。见 §8.1。
> 2. **Web 端补偿了 iOS 的缺口**：不做 iOS 原生的最大损失是"iPhone 用户进不来"，而 iOS 16.4+ 的 Safari 恰好能承担观看端、文件端与语音端。

## 1. 先说结论（给赶时间的人）

1. **你的需求本质是"一个东西"**：一条任意两设备之间、端到端加密、可复用多路数据流的实时连接。屏幕、摄像头、投屏、文件、文字、语音全都是这条连接上的不同"频道"。不要按功能开发，要按**一条通道 + N 种频道**开发。
2. **"投屏"不是独立功能**，它是"看"的一种 UI 呈现方式（把远程画面全屏/置顶显示）。把它单独立项会写出第三套采集编码逻辑。
3. **4 个原生平台能力不对等**，"跨平台"不等于"每个平台都能当被看端"：
   - **被看 + 观看全通**：Windows、Linux(X11)、macOS —— 这是产品的基本盘
   - **被看可行但有硬伤**：Android（**每次会话都要重新授权**，后台易被杀）；Linux Wayland（抓屏每次要走门户选择）；macOS（授权后须重启 App，且系统会周期性弹权限提示）
   - **所有平台都能当好"观看端/文件端/消息端"**
4. **Web 客户端不是"阉割版"，它覆盖了大部分功能**：观看、投屏、摄像头源、文件、文字、实时语音都能做，且**浏览器自动硬解视频**、体验在"看"这件事上最好。但四类能力**根本做不到**（不是难，是没有 API）：被控端、后台静默传输、本地路径/目录静默写入、系统音频采集。
5. **Rust + 纯 Rust UI 在 5 个目标上依然不成熟**，但不是"没有答案"：**纯 Rust 路线选 Slint**（1.18.x，GPLv3 档位与本项目天然契合）；**要成熟度则选 Flutter + flutter_rust_bridge**。关键是**核心层纯 Rust、UI 层可通过 FFI 替换**，见 §6 与 `docs/research/ui-frameworks.md`。
6. 最大的三个**技术**不确定性：**移动端视频零拷贝、桌面文字清晰度（必须自研脏矩形）、NAT 穿透成功率 × 中继带宽成本**。这三个必须先用一两周探针证伪，再谈产品。**注意：Web 端会把一部分流量从 P2P 挤到中继，直接影响成本模型，见 §6.3。**

**范围已收敛**：FR-11（远程控制）明确不做，这是放弃约一半工作量的决定，也让安全模型大幅简化——不再需要"被控端强提示 + 可随时中断 + 白名单"这套机制。
FR-2（远程看桌面）与 FR-5（投屏）**本阶段同样不做**，屏幕这边的采集—编码—显示管线整条砍掉；下面的清晰度论证作为依据留档。

**但要注意"看"本身也有暗坑**（屏幕这一路本阶段不做，依据留档）：FR-2「远程看桌面」的清晰度要求远高于普通视频（逐字阅读），这需要自研脏矩形差分，见 §6.3 风险 R2。

## 3. 架构核心洞察：一条通道，三种流

所有功能归约为三种数据流，这个抽象是整个项目的骨架：

| 通道 | 承载什么 | 特性要求 | 典型实现 |
|---|---|---|---|
| **① 实时媒体流** | 屏幕画面、摄像头画面、麦克风音频 | 低延迟优先，允许丢帧，可自适应码率 | WebRTC 音视频轨（SRTP）/ QUIC datagram |
| **② 可靠字节流** | 文件、剪贴板大对象、录屏回放 | 必达、有序、可分块续传、可后台 | QUIC stream / WebRTC DataChannel(ordered) |
| **③ 消息与控制流** | 文字消息、桌面提示、控制指令、信令 | 必达、有序、小、低延迟 | DataChannel(reliable) / 小 QUIC stream |

**统一会话模型**：

```
设备身份(密钥对) → 配对(信任关系) → 会话(加密通道) → 能力协商 → 频道复用
                                                    ├─ screen:video
                                                    ├─ camera:video
                                                    ├─ mic:audio
                                                    ├─ files
                                                    ├─ clipboard
                                                    ├─ text / notify
                                                    └─ control(可选)
```

这么做的收益：
- 文件传输、消息、投屏共用同一套连接、鉴权、重连逻辑，不需要各自造轮子。
- "手机摄像头投屏到电脑" = 手机开 `camera:video` 频道，电脑开一个投屏窗口订阅它。零新增管线。
- "文字提示到桌面" = `notify` 频道 + 被提示端的托盘常驻程序。
- 后续加"远程控制"只是多一个频道，不动底座。

### 3.1 连接方式：P2P 优先 + 两处受控例外（已定）

**原则：数据默认走设备间直连；服务器在密码学上无法读取任何内容。**

| 组件 | 角色 | 承载用户数据？ | 能否解密？ |
|---|---|---|---|
| 信令服务器 | 交换候选地址、协调打洞、交换公钥 | ❌ 仅元数据 | — |
| STUN | 反射公网地址 | ❌ | — |
| TURN / 中继 | **打洞失败时的兜底转发**（已定允许） | ⚠️ 转发密文 | ❌ 不能 |
| 消息后端 | **对方离线时的密文暂存**（已定需要） | ⚠️ 暂存密文 | ❌ 不能 |
| 设备 ↔ 设备 | **默认数据路径** | ✅ | ✅ |

**两处例外要说清楚，因为它们让"纯 P2P"变成了"P2P 优先"：**

1. **打洞失败 → 中继兜底**（决策 7）。这是可用性与纯粹性之间的取舍：通用 WebRTC 产品的回退率约 **15–25%**，企业 WiFi / 受限移动网络更高，**CGNAT 场景接近 100%**。选择兜底意味着**没有用户会被彻底挡在门外**，代价是中继带宽成本——所以 **"中继占比"要从 M0 起作为 KPI 埋点，目标 <15%**。
2. **对方离线 → 服务器暂存密文**（决策 8）。这解决了"P2P 要求双方同时在线"的硬伤，让语音消息与文字消息真正可用。**但代价是你要运营一个消息后端**，而且暂存的密文必须做到服务器不可读——这要求**双棘轮（Double Ratchet）**这类前向安全方案，不是简单的"用设备公钥加密存起来"。同时要定好保留期、删除策略与多设备同步。

**保留 P2P 的边界因此是清楚的**：屏幕、摄像头、麦克风这类**实时媒体永不走服务器**（除了打洞失败时的中继密文转发）；文件走设备直连；只有**离线消息**是 store-and-forward。

**还有两条硬事实不变：**
- **实时媒体仍然要求双方同时在线**。异步可达只救得了消息，救不了"看桌面"——对方关机就是看不了，这必须有明确的 UX 提示。
- **Web 端不能用 WebTransport**：`WebTransport`（HTTP/3）虽然已 Baseline 2026、Rust 侧有 `wtransport`，但它是 **client↔server 模型，流量必须过中继**，与 P2P 原则冲突，因此撤出方案。**Web 端文件传输走 WebRTC DataChannel**（浏览器 WebRTC 是真 P2P，可与原生端互通），代价是超大文件的吞吐与续传体验弱于原生 QUIC。

## 4. 角色矩阵：不是每个平台都能当"源"

这是本项目最容易踩的坑。产品形态应该按这个矩阵来定，而不是假设所有端对称。
**注意：已决定不做远程控制**，所以下表的"输入注入"行仅作背景参考，不是本轮需求。

| 能力 \ 端 | Windows | Linux(X11) | Linux(Wayland) | macOS | Android | **Web** |
|---|---|---|---|---|---|---|
| 采集屏幕 | ✅ DXGI/WGC | ✅ XShm | ⚠️ PipeWire+门户，每次要授权 | ✅ ScreenCaptureKit + TCC 授权（授权后须重启 App） | ⚠️ MediaProjection，**Android 14+ 每次会话重新授权** | 🟡 仅前台、**每次都要手势 + 重新选源** |
| 采集摄像头 | ✅ | ✅ V4L2 | ✅ V4L2 | ✅ AVFoundation | ✅ Camera2（需前台服务+常驻通知） | ✅ **Web 的最佳用途**（授权一次即可） |
| 采集系统音频 | ✅ WASAPI loopback | ⚠️ PulseAudio/PipeWire monitor | ⚠️ 同上 | ⚠️ ScreenCaptureKit 音频 | ⚠️ 仅 usage=MEDIA/GAME 且策略允许时可录，**不可承诺"听到任何声音"** | ❌ **浏览器无等价 API**，无法采集其他应用的音频 |
| 硬件编解码 | ✅ NVENC/QSV/AMF | ⚠️ VAAPI 碎片化 | ⚠️ 同左 | ✅ VideoToolbox | ✅ MediaCodec（机型差异大） | ✅ 浏览器自动硬解（播放侧最省心） |
| 观看/解码显示 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ **强项** |
| 后台常驻推流 | ✅ 服务/托盘 | ✅ 守护进程 | ✅ | ⚠️ 沙盒+公证 | ⚠️ 厂商省电策略会杀 | ❌ 页面关了就没了 |
| 收文件/消息/通知 | ✅ | ✅ | ✅ | ✅ | ✅ | 🟡 需前台；通知需授权，**iOS 需"添加到主屏幕"** |
| （背景）输入注入 | ✅ SendInput | ✅ XTest/uinput | ⚠️ 仅 GNOME/KDE 支持 portal RemoteDesktop | ⚠️ CGEvent + 辅助功能授权 | ⚠️ 无障碍服务，商店政策受限 | ❌ 不可能 |

**由此得出的产品定位建议**：

- **"被看端"只做桌面三平台**（Windows / Linux / macOS），这是能提供完整体验的地方。手机端和 Web 端都以"看"和"摄像头源"为主。
- **Web 端的定位是"免安装的观看端 + 文件端 + 摄像头源"**，并对 iPhone/iPad/Chromebook 提供唯一入口。Web 端顺带支持"共享浏览器标签页"，但**不要当卖点**（每次重选源，体验明显弱于原生）。
- **iPhone/iPad 用户的接入路径是 Safari，不是 App**：iOS 16.4+ 的 Safari 可当完整的观看端 + 文件端 + 语音端。这是"不做 iOS 原生"这个决策能被接受的关键——**代价比看起来小得多**。
- **Web 端有四件事是硬边界，不是"难"**（产品文案不要承诺）：① 被控端（无输入注入 API）；② 后台静默传输/关页续传；③ 本地任意路径与目录的静默写入；④ 系统音频采集。详见 `docs/research/web-client-capabilities.md`。
- **Linux 必须区分 X11 / Wayland，并且要意识到 X11 是正在消失的技术债**：GNOME 49 已默认禁用 X11 会话、计划 GNOME 50 移除，Fedora KDE 40 起不再提供 X11 会话。**Wayland 才是必须攻克的主线**：抓屏要走 portal + PipeWire（用户每次点选共享哪个屏幕）。要在 UI 上提前设计好引导。
- **macOS 有两个易被低估的摩擦**：屏幕录制权限**授权后必须重启 App 才生效**，且 macOS 15 会对使用已弃用采集技术的 App **反复弹窗提示、无法永久关闭**（缓解办法是改用 `SCContentSharingPicker`）。产品文案要提前解释，否则用户会以为是 bug。

## 5. 非功能需求（可量化，用来验收）

| 维度 | 目标 | 说明 |
|---|---|---|
| 端到端延迟（玻璃到玻璃） | 局域网 ≤ 150ms；公网 P2P ≤ 300ms；投屏场景 ≤ 200ms | 采集 5–16ms + 编码 5–15ms + 网络 20–150ms + 解码 5–10ms + 渲染/合成 16–33ms |
| 带宽 | 自适应 500 kbps – 20 Mbps | 桌面文字场景需要高码率保清晰度；摄像头场景可低码率 |
| 连接建立时间 | 局域网 < 1s；公网 P2P < 3s（含打洞） | 打洞失败走中继要更快回退，不能卡住用户 |
| 断线重连 | 网络抖动/切网后 < 3s 恢复，画面不断会话 | 移动端 4G↔WiFi 切换是必测场景 |
| 画质 | 桌面文字"可读"为硬指标 | 远程桌面的清晰度需求 ≠ 普通视频，见 §6.3 |
| CPU/功耗 | 手机端连续推流 30 分钟不过热降频 | 必须走硬编，帧率可降 |
| 内存 | 桌面端 < 300MB；Web 端 < 500MB；手机端推流时 < 400MB | 超限会被系统/浏览器标签页回收 |
| 安全 | 端到端加密；**服务器零知识**（信令/中继/消息暂存均无法解密）；离线消息用双棘轮前向安全 | 配对需防中间人（二维码 + 短数字校验） |
| **连接方式** | ✅ **已定：P2P 优先**；打洞失败走中继密文转发；离线消息走服务器密文暂存 | 中继占比目标 <15%；详见 §3.1 |
| 隐私 | 被采集时**必须**有不可忽略的可见提示；可随时一键中断 | 也是法律合规要求 |
| 可用性 | 无人值守访问需显式开启 + 独立凭据 + 白名单 | 这是最大的滥用风险面 |
| 平台 | 原生：Windows 10 1809+ / Ubuntu 20.04+·Debian 11+ / macOS 12.3+ / Android 10+；Web：Chrome/Edge 现代版、Safari 16.4+、Firefox 现代版 | 版本下限直接决定可用 API |

## 6. 技术选型分析

### 6.1 最重要的一条建议：核心与 UI 解耦

你说"Rust + 类 Flutter 的 UI 库"。这里有一个必须先说清楚的事实：**目前没有任何一个纯 Rust UI 框架在 4 个原生平台（尤其 Android）上达到生产级成熟度**。如果把 UI 和业务逻辑焊死，将来换 UI 框架等于重写。

而现在你多了**第四个 UI 目标：Web**。好消息是 **Rust 核心可以编译成 WASM 跑在浏览器里**——加密、协议、分块传输、状态机这些纯逻辑可以复用；坏消息是**采集与编解码不能复用**（浏览器的采集/编解码 API 不在 Rust 手里）。所以 Web 端的复用边界要说清楚：

```
可复用（Rust → WASM）       不可复用（必须写浏览器代码）
─────────────────────      ────────────────────────────
协议与消息编解码            屏幕/摄像头采集（getDisplayMedia/getUserMedia）
加密与身份、配对            编解码（浏览器 WebRTC/WebCodecs 自带）
文件分块、哈希、续传状态机    渲染（<video> 元素，不需要 Rust 参与）
会话状态机与能力协商         文件落盘（File System Access API）
```

所以架构上必须分三层：

```
┌─────────────────────────────────────────────┐
│ UI 层（可替换）                              │
│  Flutter(Dart) / Slint / 平台原生            │
└───────────────┬─────────────────────────────┘
                │ C ABI 或 flutter_rust_bridge（稳定接口）
┌───────────────┴─────────────────────────────┐
│ 会话编排层（Rust，无 UI 依赖）               │
│  会话状态机 / 能力协商 / 重连 / 权限提示事件  │
└───────────────┬─────────────────────────────┘
┌───────────────┴─────────────────────────────┐
│ 能力实现层（Rust + 少量平台原生）            │
│  采集 / 编解码 / 传输 / 加密 / 文件 / 消息    │
└─────────────────────────────────────────────┘
```

- **UI 层只做三件事**：显示视频帧、显示状态、发出用户意图。它不认识 WebRTC，也不认识编码器。
- **视频帧的传递是性能关键路径**：UI 层必须能高效接收帧（理想是 GPU 纹理/共享句柄零拷贝，退一步是共享内存 + 硬件解码器输出直通）。选 UI 框架时这是第一硬指标，不是"长得好看"。
- 这样选型可以后置：先按 Flutter + flutter_rust_bridge 或 Slint 起步，二者都能换。

### 6.2 UI 框架候选

详见 `docs/research/ui-frameworks.md`（354 行，6 张对比表，版本号经 crates.io / GitHub API 核实）。要点：

- **Slint（1.18.x）——纯 Rust 路线的唯一合理答案**：官方覆盖 Android（`backend-android-activity-06` + `cargo apk2`）与 iOS；**GPLv3 档位与本项目天然契合、零费用零归因义务**（官方明确"你自己的文件可保持 MIT/Apache-2.0"）；且官方恰好有 `examples/wgpu_texture`、`examples/opengl_texture`、`examples/ffmpeg` 三个对口的视频导入示例（经 `Window::set_rendering_notifier` + `GraphicsAPI` 拿外部纹理）。
  **硬伤有两个**：① **零拷贝平台不对称**——`slint::Image` 只有 `from_borrowed_gl_2d_rgba_texture`，**没有 D3D11/Metal 借用 API**，意味着 Windows/macOS 上的 4K60 零拷贝要自研 wgpu 桥；退化成 CPU 上传则是 1080p60 ≈ **498 MB/s**、4K60 ≈ **2 GB/s** 的带宽压力。② Android 上有 5+ 个未闭合的 **IME/软键盘 issue**（SwiftKey、软键盘闪烁、`request_redraw` 失效），直接命中你的"文字消息"功能——**这是移动端中文输入体验的现实风险**。
- **Flutter + flutter_rust_bridge（FRB 2.13.x）——成熟度最高的现实答案**：移动端外部纹理是官方能力（`SurfaceProducer`/`FlutterTexture`），桌面端由 **`irondash_texture`**（MIT）补齐 Windows `D3D11Texture2D`/DXGI 共享句柄、Apple `IOSurface`、Linux `GLTexture`、Android `ANativeWindow`；FRB 的 `ZeroCopyBuffer` 解决跨语言大块拷贝。代价：UI 是 Dart（不是纯 Rust），且 `irondash_texture` 稳定版 0.5.0 停在 2023-12、下载量小（约 519/月），需自担维护风险。
- **egui 是本次调研最反直觉的一条**：它的视频能力全表最强（`egui_wgpu::Renderer::register_native_texture` 直接吃 `wgpu::TextureView`，真零拷贝）。在原来的"含 iOS"范围下它因 **eframe 只有 Android feature、没有 iOS** 直接出局；**砍掉 iOS 之后它的排除理由变弱了**，值得在 M0 探针里重新评估（但它没有 iOS 也意味着生态重心在桌面，Android 端成熟度需实测）。
- **Dioxus / Tauri v2 走 WebView，与实时视频结构性冲突**：帧只能 Rust → IPC/blob → JS → `texImage2D`，或干脆放弃 Rust 解码改用 JS WebCodecs，跟"Rust 实时视频核心"的目标矛盾；且移动端 open issue 很多（Dioxus Android 26 个、Tauri Android 119 个）。
- **Makepad 最能说明"纯 Rust 移动端"的现实**：它内部**已经**实现了零拷贝（`VideoExternal`/`OES`/`CVMetal`），但公开 API 至今仍是零评论的 open 提案，且移动端有未修的输入崩溃问题。
- **Ribir 已停滞**（最后提交 2026-04、无移动端）；**iced** 官方定位仅 Win/macOS/Linux/Web；**Xilem** 自称 experimental；vizia/Freya 无移动端。
- **平台原生 UI**（SwiftUI / Compose / WinUI / GTK）性能与合规最优，代价是 UI 写 4 遍、4 套 CI。**建议保留为性能兜底的备选。**
- **Web 端不是一个"UI 框架选项"，而是一个独立目标**：它就是 HTML/CSS/JS + 编译到 WASM 的 Rust 核心。它的视频显示靠浏览器自己的 `<video>` + WebRTC，**不需要任何 Rust UI 框架参与，也不需要零拷贝桥**——从"看视频"这件事上说，Web 反而是所有端里最省心的。它的难点在别处（采集受限、无后台、HTTPS 要求），见 §4。

> 结论：**不要为了"纯 Rust"这个审美目标，牺牲交付能力。** 现在是三选一：
> - 想要**纯 Rust 的技术纯粹性** → Slint，并接受"Windows/macOS 零拷贝要自研 + Android 输入法有风险"。
> - 想要**最快、最稳地交付 4 个原生端** → Rust 核心 + Flutter 壳（FRB），接受 UI 是 Dart。
> - **不确定就先别定** —— 已决定由 M0 探针实测后决定（见 §0 决策 4）。
>
> 三者的共同前提都是 §6.1 的**核心与 UI 解耦**——只要这条守住了，换 UI 框架就是换一层壳。把 Rust 的优势集中在采集、编解码、传输、加密、性能上，那才是 Rust 真正创造价值的地方。

### 6.3 传输与媒体栈

详见 `docs/research/transport-media.md`（含 crates.io 版本核实、成本模型、参考链接）。**推荐组合**：

| 层 | 选型 | 一句话理由 |
|---|---|---|
| 媒体通道 | `webrtc-rs` 0.21.x（**不要用 0.17 分支**）+ ICE 打洞 | ICE/BWE/NACK/FEC/DTLS-SRTP 全部白拿，自研是几个月的工作量 |
| 中继兜底 | 自建 coturn 集群 + 自研信令 relay | 中继只转发密文、服务器零知识；必须支持 TCP/443 回退穿透企业防火墙 |
| 文件通道 | 原生↔原生：**独立 QUIC 连接（P2P）**；Web 参与时：WebRTC DataChannel | 见下方修正 1 |
| 消息/控制（在线） | 与文件共用 QUIC 连接上的小 stream + Noise_IK | 必达、有序、低延迟 |
| 消息（离线） | 服务器**密文暂存** + **双棘轮（vodozemac）** | 见下方修正 3 |
| 编解码 | H.264 High Profile 硬编优先 + openh264 兜底；HEVC 可选；**AV1 暂缓** | 硬解覆盖率 + WebRTC 互通性；AV1 在屏幕共享场景仍有实际 bug |
| 桌面文字 | **脏矩形/瓦片差分 + 区域分类混合编码** | 收益比"换编解码器"大一个数量级 |
| 加密 | DTLS-SRTP（逐跳）+ SFrame 端到端帧加密（RFC 9605） | 中继能转发但不能读 |
| 身份配对 | Ed25519 + X25519 + 二维码带外 + SPAKE2 六位码 + SAS 比对 | 服务端零知识且防中间人；**禁止纯在线首次配对** |
| 明确不上 | SFU（LiveKit/mediasoup）、libp2p、WireGuard、纯自建 UDP、WebTransport、自研 QUIC 媒体层 | 与 P2P 原则冲突或收益为负 |

**已定决策带来的三处修正（必读）：**

1. **原生↔原生的独立 QUIC 文件通道 = 第二条 P2P 路径。** 你已选定这条路，请注意它的真实代价：`quinn` 只是 QUIC 库，**不含 NAT 穿透**，所以第二条路径要自己做打洞/保活/迁移。两条实现路径：
   - **a) 复用 WebRTC 的 ICE**：`webrtc-rs` 0.21 已是 sans-I/O 架构，理论上可以自己驱动 ICE agent 完成打洞，再把选中的 socket 交给 `quinn`。省一套中继，但粘合层要自己写，且踩在库的新 API 上。
   - **b) 用 `iroh` 跑原生文件通道**：iroh 1.x 开箱提供 QUIC 流 + 打洞 + 中继，正好覆盖这个需求，几乎不用自己写穿透。代价是**第二套连接栈与第二个中继**（coturn 之外再加 iroh relay），运维复杂度上升。
   > **建议 M0 阶段用一两天做个对比实验再选**：判据是"第二条路径的建立成功率、代码量、以及是否愿意多运维一套中继"。
2. **Web 端不能走 WebTransport。** 它虽已 Baseline 2026、Rust 侧有 `wtransport`，但属于 **client↔server 模型，流量必须过中继**，与 P2P 原则冲突，已撤出方案。**Web 端文件传输只能用 WebRTC DataChannel**（浏览器 WebRTC 是真 P2P，可与原生端互通）；代价是 Web 端大文件吞吐与续传体验弱于原生。
3. **离线消息后端是一个新增的运营组件。** 你已选择"异步可达"，这意味着要自建消息暂存服务，并且**必须用双棘轮（`vodozemac` 0.11）而不是"设备公钥加密存起来"**——因为暂存的密文需要在服务器被攻破时仍然安全（前向安全 + 后向安全）。同时要定义清楚：保留期、送达后删除、多设备同步、以及"对方永不上线"时的过期策略。**这块不要低估，它是一个完整的小后端。**

三点补充判断：

- **文件名里的 "Relay" 是对的方向**：对称 NAT / CGNAT 下必须兜底。但要**中继零知识**——服务器只转发加密包，被攻破也不泄露内容。成本模型：1080p 中继约 **1.8 GB/小时**（单向），云出口价差可达 8 倍，因此**"中继占比"要作为 M0 就开始埋点的 KPI，目标 <15%**。
- **桌面文字清晰度是唯一"选对库也解决不了、必须自研"的部分**。通用编码器的率失真优化会主动牺牲文本高频细节，而远程桌面用户是逐字阅读。参考实现的两条路：Sunshine/Moonlight 靠高码率硬扛（游戏思路），RDP 靠脏矩形 + 图元/无损区域。**脏矩形差分要作为 M1 必做项，而不是优化项。**
- **要接受"桌面场景"和"摄像头场景"是两条不同的编码路径**，不要试图用一套参数统一。

### 6.4 建议的工程结构

```
SecRelay/
├─ crates/
│  ├─ secrelay-protocol/    # 消息定义、能力协商、版本兼容
│  ├─ secrelay-crypto/      # 设备身份、密钥交换、E2EE、双棘轮（离线消息）
│  ├─ secrelay-transport/   # 连接抽象：ICE 打洞 / 中继 / QUIC 文件通道（三条路径收敛到一个 trait）
│  ├─ secrelay-media/       # 采集/编解码/渲染抽象 + 平台后端（曾实现的屏幕采集部分本阶段已移除）
│  ├─ secrelay-session/     # 会话编排、状态机、频道管理、重连
│  ├─ secrelay-transfer/    # 文件与剪贴板传输
│  ├─ secrelay-notify/      # 桌面提示与消息
│  ├─ secrelay-core-wasm/   # 编译到 WASM 供 Web 端复用的子集（协议/加密/分块）
│  └─ secrelay-ffi/         # C ABI / flutter_rust_bridge 绑定
├─ apps/
│  ├─ desktop/              # 桌面 UI（框架待定）
│  ├─ mobile/               # Android UI
│  ├─ web/                  # Web 客户端（HTML/JS + secrelay-core-wasm）
│  └─ server/               # 信令 + TURN 协调 + 离线消息暂存（零知识）
└─ docs/
```

关键点：
- `crates/*` **不允许依赖任何 UI 框架**，这条用 CI 强制检查（否则半年后一定会烂）。
- `secrelay-transport` 要把**三条路径**（WebRTC/ICE、TURN 中继、QUIC 文件通道）收敛到**一个 trait 抽象**后面。这是应对"webrtc-rs 生态动荡"和"文件通道实现路径未定"的关键隔离层。
- `secrelay-core-wasm` 只放**能复用的纯逻辑**（协议、加密、文件分块/哈希/续传状态机），不要试图把采集和编解码也塞进去。

## 7. 风险清单与"一周探针"验证

大项目的正确做法是：先花一周把最可能推翻方案的风险打掉，再投入。

| 级别 | 风险 | 影响 | 一周内可做的探针 | 判据 |
|---|---|---|---|---|
| **P0** | **P2P 打洞成功率不足**（已定 P2P 优先 + 允许中继兜底） | 中继占比升高 = 带宽成本失控（1080p 中继约 1.8GB/h·单向，云出口价差可达 8 倍） | 部署 coturn，跨运营商/4G 实测打洞成功率 | 直连成功率 > 80%（中继占比 <15%） |
| **P0** | **第二条 P2P 路径（QUIC 文件通道）实现未定**（新） | M1 可能卡在打洞/保活/迁移细节上 | 用小 demo 实测对比：**a) 复用 webrtc-rs 的 sans-I/O ICE + `quinn`** vs **b) 用 `iroh` 直接跑文件通道** | 建立成功率、代码量、以及是否愿意多运维一套中继（iroh relay） |
| **P1** | **离线消息后端是一个完整的小服务**（新） | 排期被低估；前向安全做错会直接毁掉"服务器零知识"的承诺 | 用 `vodozemac` 做最小 store-and-forward 闭环，并做"数据库被拖走"的威胁模型评审 | 攻击者拿到完整数据库也解不出任何明文 |
| **P0** | Wayland 抓屏受限，且 X11 正在消失 | Linux 体验崩塌（舒适区有时间窗） | Ubuntu 24.04+ Wayland 用 PipeWire 抓屏，实测授权流程与帧率 | 能连续 1080p60；确认 portal 授权是否可记忆 |
| **P0** | WebRTC Rust 生态动荡，可能"押错版本" | M2 阶段被迫 fork 或换库 | webrtc-rs 0.21 建/销 1000 条连接，测内存曲线 | 无线性增长（旧版有 ~109KiB/连接的泄漏） |
| **P0** | 4 原生端 UI + 视频零拷贝不达标 | 交付不了 / 画面卡顿 | 用候选框架各做一个"接收并显示 1080p60 视频"的 demo | 稳定 60fps、能打包；**Windows/macOS 若走 Slint 需自研 wgpu 桥并实测** |
| **P0** | **Web 端与 P2P 的组合**（新） | 方案可能返工 | 用浏览器 WebRTC 与原生端建 P2P 连接，传一个大文件；再测 `getDisplayMedia` 的真实体验 | 浏览器能与原生 P2P 互通、文件吞吐可接受、屏幕共享的授权流程可接受 |
| **P1** | Android 14+ 每次会话重新授权 | 用户体验差（断线重连=重弹授权） | 实测 MediaProjection 授权行为与前台服务 | 官方已确认实例一次性，**不要指望"一次授权多次使用"**，要设计好重连话术 |
| **P1** | 硬件编解码碎片化 | 兼容性差 | 在 3 台不同年代 Android 机 + 3 台 PC 上测编解码 | 覆盖率，需不需要软编兜底 |
| **P1** | 桌面文字清晰度不达标 | 核心体验差，且返工点在采集→编码管线 | 量化"1080p 静态文档可读的最低码率" | 建议指标：≤2Mbps 时 OCR 准确率 >99% |
| **P1** | **实时语音对讲是独立子系统**（新） | 排期被低估，回声/噪声问题毁体验 | 做最小双向语音 demo，实测回声消除与延迟 | 手机外放+对讲无啸叫，延迟 <200ms |
| **P1** | 手机发热/耗电 | 移动端体验差 | 手机推流 30 分钟温度与电量曲线 | 是否必须降到 30fps |
| **P1** | Slint 在 Android 的 IME/软键盘问题 | 中文输入体验受损 | 在目标机型上实测中文输入法、软键盘弹出与重绘 | 若不可接受 → 移动端转 Flutter 或平台原生 |
| **P2** | Web 端 HTTPS 要求与"局域网直连"冲突 | 内网自建场景下 Web 端不可用 | 试自签证书/内网域名下 Web 端实际能跑多少功能 | 确定 Web 端是否只做公网域名场景（D21） |
| **P2** | 安全与滥用（无人值守被入侵） | 严重事故 | 设计评审：配对、密钥、白名单、可见提示 | 威胁模型评审通过 |

> 说明：平台调研中有两项因本机网络不可达**未能逐字核实**（Google Play 无障碍 API 申报要求、`CGEvent.post` 被 Guideline 2.4.5 拒审的案例）——现已因"不做远程控制"而基本不相关。Web 端调研里的浏览器版本号取自 MDN Baseline 标注与规格**推断**，动工前需用 caniuse + 真机实测复核（原文已标 ⚠️）。

## 8. 法务与合规

### 8.1 ~~GPLv3 与 App Store 冲突~~ → **已因"不做 iOS"而消解** ✅

原本这是本项目**最大的非技术风险**：项目是 GPLv3，而 App Store 服务条款与 GPL 不兼容（VLC 下架案的根源，FSF 曾实际执法）。**决策 1（不做 iOS 原生版）直接让它消失了。**

剩下的两个相关事项：

- **macOS 分发不走 MAS 即可**：用 Developer ID 签名 + 公证（notarization）直接分发，GPLv3 没有障碍。**但如果将来想上 Mac App Store，同一冲突会再出现**（沙盒与 GPL 的兼容性另有争议），届时需要重新评估。
- **Web 端要留意 GPLv3 与 AGPLv3 的差别**：GPLv3 的源码义务只在**分发**时触发，**单纯的网络服务不触发**（这正是 AGPL 要补的洞）。你的 Web 端会把 Rust/WASM 与 JS 分发到浏览器，**属于分发，需要提供对应源码**——对开源项目没问题。但如果你希望**防止别人拿你的代码搭一个闭源托管服务**，那应该考虑 **AGPLv3**。这是一个值得现在就想清楚的选择（换成 AGPL 同样需要所有贡献者同意，现在只有你一个人，最便宜）。

### 8.2 App Store 远程桌面条款 4.2.7 → **不再适用** ✅

该条款只约束 iOS App Store 上的应用。不做 iOS 原生版即不适用。**但保留一条经验**：如果将来要重做 iOS，4.2.7 会约束"host 与 client 必须同一 LAN"这类定位，届时需重新评估。

### 8.3 编解码许可（仍然有效）

H.264 的 Via LA 2026 新费率 Tier 1 达 **$4.5M/年**。个人/小项目大概率落在 "small or nascent" 档（约 10 万美元量级），但这是一个**真实的年费成本**，不是零。

**架构上的应对**：协议层保留**编解码可切换能力**，以便将来用 HEVC/AV1 规避；同时把这个决策点显式化（见 D15）。不要等到产品要商业化时才发现编解码许可没算进成本模型。

### 8.4 其他合规项

- **隐私**：被采集端必须有不可忽略的可见提示、可随时一键中断（也是多地法律要求）。**Web 端尤其要注意**：浏览器自带的"正在共享"提示帮了忙，但也意味着用户对"能静默采集"有错误预期，产品文案要写清楚。
- **跨境/出口**：使用强加密，部分市场有合规申报要求。
- **HTTPS 是 Web 端的硬前提**：所有关键 API（`getUserMedia`/`getDisplayMedia`/WebRTC/WebTransport/Push）都要求 secure context，`http://localhost` 是唯一实用例外。**纯内网 IP + 自签证书下 Web 端基本不可用**——这与"局域网直连可用"（D8）存在直接冲突，见 D21。

## 11. 一句话总结

你的需求本质上是**一个跨平台、端到端加密、设备间直连（P2P）的"实时连接层"，上面挂三类频道（实时媒体 / 可靠文件 / 消息控制）**；功能列表里"投屏"是显示形态、"看摄像头"和"看桌面"是同一条媒体管线、"传文件"和"发消息"是同一类可靠通道。真正要提前解决的不是"功能太多"，而是几个**可行性**问题：**P2P 打洞成功率与中继策略、桌面文字清晰度（必须自研脏矩形）、Wayland 抓屏、移动端视频零拷贝、实时语音子系统**，以及 Web 端与 P2P 的组合验证。建议先做 M0 探针，再定 UI 框架和里程碑。

**如果只记四句话**：
1. 按"一条加密通道 + N 种频道"设计，不要按功能列表设计。
2. 别假设各端对称——**桌面三端是唯一完整的被看端**，Android 的痛点是授权不是技术，Web 是免安装的观看端/文件端/摄像头源（但四类能力永远做不到）。
3. **"P2P" 在你的项目里是 "P2P 优先 + 两处受控例外"**：打洞失败走中继密文转发、对方离线走服务器密文暂存。实时媒体永不过服务器；能守住这条，"零知识"这句话就站得住。
4. 先做探针证伪风险，并想清楚许可证（GPL vs AGPL）；这两件事都比写代码更早决定项目成败。

**下一步的四个动作**（全部在 M0 内可完成）：
① 部署 coturn 实测打洞成功率 → 定下中继占比基线；
② 对比实验：文件通道用"复用 ICE + `quinn`"还是 `iroh`（D24）；
③ 用"显示 1080p60 视频"的 demo 定 UI 框架（D6）；
④ 定许可证 GPL vs AGPL（D23）。
