# ADR-0003：连接阶梯 —— 按成功率排序，Mesh 优先于服务器中继

- 状态：已采纳
- 日期：2026-10-06
- 关联：`SecRelay-Relay/docs/adr/0001-media-fallback-sfu.md`、`docs/adr/0002-frame-forwarding-broadcast.md`

## 背景

连接策略原先只写了「P2P 优先，中继兜底」，但**没有规定 P2P 内部按什么顺序尝试**，
也没有区分中继是谁在承担。实测暴露出两个问题：

1. 我们只做了 **UDP 打洞**，没有 IPv6、没有 UPnP、没有 TCP 打洞，成功率被压低。
2. 中继**全部由服务器承担**。移动网络（实测中国移动 CGNAT）打洞在原理上不可能成功，
   这类连接会长期占用服务器带宽。

## 决策

连接按**成功率从高到低**依次尝试，前一档成功就不进入下一档：

| 顺序 | 方式 | 前提 | 是否消耗服务端带宽 |
|---|---|---|---|
| 1 | **IPv6 直连** | 双方都有可用 IPv6 | 否 |
| 2 | **UPnP / NAT-PMP 直连** | 有公网 IPv4，且路由器支持并开启 | 否 |
| 3 | **TCP/UDP 打洞**（多种方式，含端口预测） | 双方 NAT 允许 | 否 |
| 4 | **Mesh 转发**（网络条件好的客户端代转） | 有可用中继节点且节点愿意承担 | **否（用别的客户端）** |
| 5 | **服务器转发** | 以上都失败 | 是 |

**IPv6 排第一**：IPv6 下没有 NAT，直连成功率最高，且实测移动网络的 IPv6 覆盖往往好于
其 IPv4 公网地址（移动网络几乎都是 CGNAT）。

**每一档都要能独立失败。** 尤其是第 1–3 档的候选收集：任何一路候选收集卡住或超时，
都不能让整轮失败（实测过一个不响应的 ICE 服务器会把整轮拖到 15 秒超时）。

## Mesh 转发（**本阶段推迟**）

> **状态：推迟，不在当前阶段实施。** 先做第 1–3 档与第 5 档，Mesh 留到之后。
> 下面的设计结论保留，实施时按此执行。

第 4 档是**让网络条件好的客户端替其它客户端转发**。

### 只服务自己的设备

Mesh **只允许为同一个人的设备转发，不对任何第三方开放**。

理由是三条，任一条单独成立就足够：

- **别人的流量会白耗你的上行带宽**，而这是用户自己的资源
- 要给别人转发就得**信任陌生节点**，而本服务明确不做账号验证，没有可信的准入手段
- 出问题时**无法追责**，也说不清是"代转"还是"被利用"

因此 Mesh 的作用域是**用户自己的设备组**，不是公共池。

### 分组从哪来

中继**不做账号验证**（硬约束），所以"哪些设备是我的"**不能由中继判定**，
只能在**客户端侧靠设备配对**建立：用户把自己的设备两两配对（配对本就是端到端加密的前提），
配对过的设备互相认得，才允许互相代转。

中继在这条路上只做**信令与密文搬运**，不参与判定谁是"自己人"。

### 实际价值在哪

"只给自己用"意味着：**用户至少要有一台网络条件好的设备，Mesh 才起作用**。

- **多设备用户 + 一台常开的家庭设备**（家用 NAS、常开的台式机）：
  让这台当节点，手机、笔记本在外网都经它中转 —— **这是 Mesh 最有价值的场景**
- **只有两台设备、且两台都在受限网络**（例如都在移动网络）：
  Mesh 帮不上，只能落到第 5 档服务器转发

所以 Mesh **不能取代服务器转发**，它是在"用户自己有好节点"时省掉服务器带宽的优化。

### 代价与约束（其余）

之所以可行，是因为本服务的转发**只搬运密文**：代转的设备**读不到任何内容**，
零知识这条约束让 Mesh 在隐私上是安全的。

- **仍然要显式同意**：代转会消耗同意者的上行带宽，不能默认开启
- 代转节点**被攻陷或作恶**时只能丢弃、延迟、篡改时序，**看不到内容**；
  被服务方应能感知并改走服务器转发
- 需要一套"我的设备"清单的通告与选择机制


## 服务器转发的传输形态

第 5 档当前实现为**经信令 WebSocket 转发密文帧**（见 ADR-0002）。它的已知代价是
**TCP 队头阻塞**：一条丢包会阻塞其后的所有帧。

替代方向：**可靠 UDP（KCP 一类）走单个 UDP 端口**。
它既不引入 TCP 队头阻塞，也**只需要一个端口**（不像 TURN 要一整个端口段）。
这一条尚未实施，作为 ADR-0002 那个代价的候选解法记录在此。

## 未决

- Mesh 节点的发现、选择与信任机制
- 是否引入可靠 UDP 替换 WebSocket 承载转发帧
- 各档的独立超时与切换策略（一档失败多久进入下一档）
- TCP 打洞的具体形态（RFC 6544 的 TCP 候选，还是自有协议）

## 实测支撑

- 家用宽带 ↔ 有公网 IP 的机器：**直连成功**
- 家用宽带 ↔ 移动网络（中国移动 CGNAT）：两端都拿到 srflx，**直连仍失败**，转发兜底成功
- 结论：**打洞成功率取决于 NAT 组合，不是实现缺陷**；而第 1、2 档（IPv6、UPnP）
  能绕开一部分本就不可能打通的组合，是提高整体成功率的关键
