# SECTL 账号系统接入设计（SecRelay）

> **定位**：本文只回答一件事——思拓创联（SECTL）自研账号系统能给 SecRelay 提供什么、**不能**提供什么，以及接入时必须遵守的硬约束。
> **前提事实**（来自 `需求分析.md` §0 / §3.1 / §6.3，不在本文重开讨论）：P2P 优先 + 中继兜底；中继**不做账号验证**；服务器一律**零知识**；离线消息需服务器密文暂存 + 双棘轮。
> **事实来源**：`D:\code\SECTL-auth\public\docs`（`index.json` version 1）。下表所有结论均标注来源文件；文档未写清的标 **需向账号系统维护方确认**，本文不编造。
> **一句话结论**：**SECTL-auth 是身份与自同步的提供者，不是消息投递系统。** 它可以做登录、资料、设备列表同步、文件中转、更新分发、遥测；**它做不了用户与用户之间的任何投递**（离线消息、桌面提示都不能借它），那些必须自建。

---

## 0. 一页结论

| 分类 | 内容 | 依据 |
|---|---|---|
| ✅ **可以直接借力** | OAuth 登录与用户身份、用户资料/头像、软件分发与自动更新检查、公开统计与遥测、"我自己的多设备"数据同步、文件上传+分享链接做的中转兜底 | §3.1 / §3.6 / §3.8 / §3.3 / §3.5 |
| ⚠️ **可借力但有硬条件** | 离线文件中转（≤100MB/文件、需 quota、链接需另一条通道递送） | §3.5 |
| ❌ **绝对不能借力** | **用户间离线消息投递、用户间文字提示到桌面**（普通用户只能给自己发通知）、**好友/联系人关系**（无社交 API）、设备私钥与双棘轮密钥托管 | §3.4 / §3.7 / §3.3 / §5 |
| 🛠 **必须自建** | 零知识消息暂存后端（vodozemac 双棘轮）、信令、TURN 中继、桌面通知投递（`notify` 频道） | §2.3 |

## 1. 能力清单

### 1.1 模块总览

来源：`API/概览/API总览.md`、`index.json`。Base URL `https://appwrite.sectl.cn`。

| 模块 | 关键接口 | 认证方式 | 关键限制 |
|---|---|---|---|
| **OAuth 登录** | `GET /oauth/authorize`、`POST /api/oauth/token`、`/api/oauth/refresh`、`/api/oauth/userinfo`、`/api/oauth/introspect`、`/api/oauth/heartbeat`、`/api/oauth/logout`、`/api/oauth/logout-all`、`/api/oauth/config` | authorize 需 **Appwrite JWT**；token/refresh/introspect 公开（PKCE）；userinfo/heartbeat/logout 需 Bearer；config 需 admin_secret | access token **3600s**；refresh token 自**首次授权**起固定 **180 天**、单次使用+轮换；`device_uuid` 必填（标准 36 位 UUID）；客户端 IP 由服务端解析 |
| **用户资料** | `/api/oauth/userinfo` | Bearer + `user:read` | 隐私开关字段**照原样返回**（不会隐藏对应值）；无 `user_data` 文档时只返回 `user_id`/`platform_id`/`login_time` |
| **Scope / 权限** | `GET /api/platform/permissions`、`GET /api/user/platforms`、`POST /api/user/permissions` | Bearer | 可用 scope：`user:read`、`cloud:read`、`cloud:write`、`cloud:peer_read`；支持 `cloud:*`、`*`、`*:*`；`permission-level`、`storage-quota`、`add-points` 等是**内部接口，外部不可调用** |
| **云存储·文件** | `GET /api/cloud/files`、`/files/{id}`、`/files/{id}/download`、`/files/{id}/preview`、`POST /api/cloud/upload`、`DELETE/PUT /api/cloud/files/{id}` | Bearer + `cloud:read`/`cloud:write` | **单文件 100MB**；列表单次最多 1000；需平台开启 `cloud_enabled`，否则 `cloud_service_disabled`；超配额 `storage_exceeded` |
| **云存储·KV** | `POST/GET/PATCH/DELETE /api/cloud/kv[/{key}]` | Bearer + `cloud:read`/`cloud:write` | **键名 ≤255 字符、值 ≤64KB、每用户每平台 ≤1000 个键**；超限 `limit_exceeded`；支持 `ttl` |
| **分享链接** | `POST /api/cloud/share`、`GET /api/cloud/shares`、`shares/{id}/disable|enable`、`DELETE` | Bearer + `cloud:write` | 有效期默认 86400s、`0` 表示永久；可设访问密码；`share_url` 形如 `https://sectl.cn/s/abc123` |
| **通知** | `POST /api/notifications/send`、`GET /api/notifications`、`{id}/read`、`read-all`、`DELETE {id}` | Bearer | **普通用户只能给自己发；管理员（`permission >= 10`）才能发给任意用户**；文档中**没有任何推送/长连接/Webhook 通道**，只有站内列表 |
| **统计/遥测** | `POST /api/stats/online`、`/api/stats/usage/increment`、`/api/stats/version`、`/api/fields/values`（全部**公开，无需认证**）；`GET /api/stats/platform/{id}`、`/api/stats/daily-metrics`、`/api/stats/region-distribution`、`/api/platform/stats/devices`（需认证） | 混用 | online 需 `device_type` 枚举；usage/increment `delta` 为 1–10000 且**未传 `period` 不会进总档**；fields/values 的字段定义必须先在后台创建否则 404；限流 120 次/分（increment）、600 次/分（version）；devices 单次最多 5000 台 |
| **软件分发** | `GET /api/software/distribution`、`/api/software/latest-tag`、`/api/software/download` | **公开读取，无需登录** | download 是 **302 跳转**（非 JSON）；多包匹配返回 409 `ambiguous_package`；**STK 只保留最近 1–2 个版本**，历史版本回落 GitHub；仓库必须已登记为软件分发项目 |
| **内容类** | 公告 `/announcements`、广告 `/api/highlights`、回声洞 `/api/echo-cave`、Hub `/api/hub`、活动参与 `/api/db/*` | 公开读 + 登录写 | 与 SecRelay 主功能无关，仅公告可作运营位；平台公告需 `permission >= 10` |
| **QQ 绑定** | `GET /api/qq-binding/status`（M2M + `qq:read`）、`/api/qq-binding/request|confirm` | M2M / Appwrite JWT | 一个账号一个 QQ、一个 QQ 一个账号；临时 Key 5 分钟失效；默认只返回脱敏号码 |
| **平台后端云服务** | `/api/v1/platform-storage/*`（quota/reservations/uploads/events/ledger） | M2M 5 分钟 token；在线叠加用户 OAuth token，离线用 delegated token | 「平台自托管文件 + SECTL 配额账本」模式；平台必须提供公网 HTTPS 管理 API（`/health`、`POST /objects`、`GET /objects/{id}`）与私有 bucket；JSON/base64 入口单文件上限 100MiB，大文件走 streaming gateway |

### 1.2 认证方式（来源：`API/概览/API总览.md`、`API/云存储/客户端云存储.md`）

| 方式 | 用途 | 备注 |
|---|---|---|
| OAuth 2.0 Bearer access token | 客户端业务请求（云存储、userinfo、heartbeat、通知读取） | 首选；`user_id` 由服务端按令牌强制回填 |
| Appwrite JWT | Web 会话；`/oauth/authorize` 唯一入口凭据 | `/api/oauth/logout-all` 只能由已登录 Web 页面 + `X-CSRF-Token` 发起 |
| Appwrite API Key | **仅服务端**；需同时传 `user_id` + `client_id` | 文档明确：`client_id:client_secret` 的 Basic 凭据**不能**用于 heartbeat 或 userinfo |
| M2M service client | 平台后端（QQ 核验、platform-storage） | 5 分钟有效；scope 需显式授予，不随 `user:read` 升级 |
| delegated / offline grant | 离线代表用户同步 | 只能保存在服务端密钥管理系统中 |

## 2. 接入边界（本节最重要）

### 2.1 分层图：账号系统只在最顶层，且可整体摘除

```
┌───────────────────────────────────────────────────────────────────┐
│ L3  账号增强层（可选插件，编译期可整体关闭）                          │
│  OAuth 登录与用户资料 · "我的设备"列表同步(KV) · 文件中转(云存储+分享) │
│  自动更新(公开分发接口，其实无需登录) · 遥测归属 · 运营公告             │
└──────────────────────────┬────────────────────────────────────────┘
                           │  单向依赖：L0–L2 不得 import 任何 SECTL 模块
┌──────────────────────────┴────────────────────────────────────────┐
│ L2  自建服务器层（零知识，与账号系统无关）                            │
│  信令 · STUN/TURN 中继（不验证账号，任何人都能连）· 离线消息密文暂存    │
└──────────────────────────┬────────────────────────────────────────┘
┌──────────────────────────┴────────────────────────────────────────┐
│ L1  会话与加密层（无条件可用）                                       │
│  设备密钥对(Ed25519/X25519) · 二维码+SIX 位码配对 · Noise/SFrame E2EE │
└──────────────────────────┬────────────────────────────────────────┘
┌──────────────────────────┴────────────────────────────────────────┐
│ L0  本地功能层（无网络、无账号也能跑）                                │
│  采集/编解码/渲染 · 局域网直连 · 本地文件 · 托盘与桌面通知             │
└───────────────────────────────────────────────────────────────────┘
```

**工程约束**：`crates/secrelay-core-*` 不得依赖 `secrelay-account`；`secrelay-account` 只允许被 `apps/*` 与 UI 调用。用 CI 检查依赖图，与 §6.4「crates 不许依赖 UI 框架」同一手段。

### 2.2 功能归属

| 能力 | 无账号（L0–L2） | 登录后解锁（L3） |
|---|---|---|
| 设备身份、配对、信任 | ✅ 本地密钥对 + 二维码/SAS | — |
| 屏幕/摄像头/投屏、实时语音 | ✅ P2P（打洞失败走中继密文） | — |
| 局域网/公网直连、文件直传 | ✅ QUIC P2P / WebRTC DataChannel | — |
| 在线文字消息、桌面提示 | ✅ `notify` 频道（对端在线） | — |
| 离线消息 | ✅ 自建暂存后端（双棘轮） | — |
| 自动更新检查/下载 | ✅ 软件分发接口**公开**，本来就不需要登录 | — |
| 遥测/版本统计 | ✅ 统计接口**公开**，本来就不需要登录 | — |
| 显示名/头像/邮箱 | ❌ 显示设备名 | ✅ userinfo |
| "我的设备"列表、跨设备设置同步 | ❌ | ✅ KV（只能同步**自己**的数据） |
| 离线文件中转（对方离线/打洞失败且中继不宜） | ❌ | ✅ 云存储 + 分享链接（≤100MB/文件） |
| 账号级设备可见性/在线心跳 | ❌ | ✅ heartbeat + 平台设备列表 |

### 2.3 三条不可越过的前提

1. **中继不得读账号**（沿用 `需求分析.md` §3.1）。中继若改为"必须有 SECTL token 才转发"，账号系统一挂全网瘫痪，且引入账号与设备身份绑定，与零知识原则冲突。
2. **信任根永远在本地密钥**：SECTL 里的"设备列表"只能用于**展示与撤销提示**，**不得**作为自动信任依据（禁止 TOFU）。新设备必须带外配对，沿用"**禁止纯在线首次配对**"。
3. **离线消息后端独立于账号系统**：它自己的可用性、保留期（D25）、鉴权都不依赖 SECTL-auth。账号最多用来给暂存记录打一个"收件人标识"。

## 3. 功能一对一映射

### 3.1 用户身份与登录（各端）

| 端 | 建议流程 | 关键约束 |
|---|---|---|
| **桌面（Win/Linux/macOS）** | 系统浏览器打开授权页 → 环回回调 `http://localhost:{port}/oauth/callback` → 拿 `code` + `code_verifier` 换 token | 环回 HTTP 回调**只有端口可变**，注册时省略端口或用 `http://localhost:*/oauth/callback`（`*` 只允许在端口位）；**强制 PKCE(S256)**；请求里的 `redirect_uri` 必须是具体地址，不能带 `*` |
| **Android** | 自定义 Scheme，如 `secrelay://oauth/callback`（或反向域名形式） | **强制 PKCE(S256)**；除端口外协议/主机/路径/查询/片段必须与注册值完全一致（即端口之外没有可变项） |
| **Web 客户端** | 复用 SECTL 的 Web 会话；`/oauth/authorize` 需 **Appwrite JWT**（`Authorization: Bearer {appwrite_user_jwt}`） | 浏览器导航**无法自定义 Authorization 头** → 必须有服务端/前端页面代持 JWT 并完成跳转。**授权入口的具体 URL 与未登录时的跳转行为：需向账号系统维护方确认** |

**风险**：`/oauth/authorize` 的 JWT 前置条件让"客户端自己发起授权"这条最简路径不成立，桌面/移动端很可能必须跳转到 SECTL 站点页面。这决定了登录 UX 与是否需要内置 WebView（**不建议**用 WebView，回调与 PKCE 易被劫持）。

### 3.2 "我的设备"列表 / 信任设备管理

| 项 | 结论 |
|---|---|
| 存放位置 | 云存储 **KV**：一键一份清单，值为**密文或公开信息**（设备名、设备公钥、最后在线时间、能力版本） |
| 为什么不是云文件 | 清单小、需要频繁整份读写；KV 支持 `PATCH /api/cloud/kv/{key}` 改字段（来源：`客户端云存储.md` §17） |
| 硬限制 | 64KB/值、1000 键/用户/平台；设备多时**必须分片或按设备分键**（如 `dev.{device_uuid}`），否则必然撞 64KB |
| **未文档化的坑** | 文档**没有**描述 KV 的并发控制（版本号 / ETag / CAS）。多设备同时整份写入很可能是 **last-write-wins 丢更新** → **需向账号系统维护方确认**；在确认前，采用"每设备一个键 + 汇总裁剪"的策略，避免整份覆盖 |
| 与 `device_uuid` 的区别 | OAuth 的 `device_uuid` 只用于 SECTL 侧设备识别与设备名生成（`User-Agent` 决定设备名），**不是** SecRelay 的设备身份；SecRelay 身份始终是本地密钥对 |
| 撤销 | 用户可在此 UI 里移除设备 = 本地信任列表删除 + 删除对应 KV 键。**注意**：删 KV **不会**吊销该设备在 SECTL 的 OAuth 令牌；普通客户端是否能吊销任意设备令牌 **需向账号系统维护方确认** |

### 3.3 联系人 / 好友关系

| 项 | 结论 |
|---|---|
| 结论 | **SECTL-auth 没有好友/联系人/用户目录接口**（`index.json` 与 `API/` 全量模块中均无；`user:read` 只能读**自己**）→ **不能借力**，SecRelay 自建 |
| 可以做的 | ① 本地信任列表（配对即信任）；② 用 KV 存**自己单侧**的联系人备注与分组（另一侧无从确认，因此不是"关系"，只是备注）；③ 用 QQ 绑定接口（M2M + `qq:read`）做"已有 SECTL 用户 ↔ QQ"的可选关联展示 |
| 风险 | KV 里只放**密文或公开信息**；昵称/备注属个人信息，建议本地加密后再上传，或干脆只存本地 |

### 3.4 离线消息：能不能用 KV 做密文暂存？**不能。**

| 判定 | 依据 |
|---|---|
| **硬性阻断** | 云存储与 KV 的数据归属是 **(平台, 用户)**，且 `user_id` 由服务端按令牌强制回填、**不能读别人的数据**（来源：`客户端云存储.md` §数据隔离）。也就是说 **A 无法把消息写进 B 的 KV**；B 也读不到 A 的数据（跨平台只读还要 4 个条件同时满足，且**只读**、写操作一律 403）→ 不存在 A→B 的投递路径 |
| **容量阻断** | 即便做"我自己多设备同步"，64KB/值 × 1000 键 只是小对象仓库：没有推送、没有消费位点、没有 TTL 语义（仅有 KV `ttl`）、没有按收件人索引 → 做不了消息队列 |
| **结论** | KV 只能做**自同步**（会话初始化、已读位点、设置、设备列表）。**离线消息必须自建零知识暂存后端**（`需求分析.md` §6.3 修正 3：`vodozemac` 双棘轮 + 保留期/送达即删策略） |

与自建后端的取舍：

| 维度 | 用 KV 暂存 | 自建暂存后端 |
|---|---|---|
| 实现成本 | 低（复用已接入的云存储） | 高（一个小后端 + 双棘轮状态机） |
| 能否 A→B 投递 | ❌ 架构上不可能 | ✅ |
| 前向安全 | 取决于自加密，但无法轮换会话 | ✅ 双棘轮 |
| 可用性风险 | 依赖 SECTL-auth | 自己掌控 |
| 元数据泄露 | 泄露给 SECTL | 自己承担（设计成最小化） |
| **决策** | 只用于自同步 | **离线消息走这条** |

### 3.5 离线文件传输 / 文件中转

| 项 | 结论 |
|---|---|
| 与 P2P 的关系 | 这是**第三方兜底**，不是主路径：P2P 直传（原生 QUIC / Web DataChannel）仍是默认；只有"对方离线、打洞失败且不愿走中继、或需要留一份限期链接"时才用 |
| 用法 | 本地加密 → `POST /api/cloud/upload`（分片，**单文件 ≤100MB**）→ `POST /api/cloud/share` 生成链接（默认 1 天、可 `0` 永久、可加密码）→ **链接本身仍要靠 SecRelay 自己的通道（P2P 或信令）递给对方** |
| 硬限制 | 单文件 **100MB**、需 `cloud_enabled`、受用户 quota 限制（超限 `storage_exceeded`）；下载/预览 URL 是**限时签名地址**（示例 `expires_at` 为 1 小时）→ 不能当长期链接 |
| 风险 | ① 密文托管在 SECTL 服务器上，**元数据**（文件名长度、大小、时间、谁分享）对 SECTL 可见；② `share_url` 形如 `https://sectl.cn/s/abc123`，**是否足够随机不可枚举、是否支持口令之外的访问控制，需向账号系统维护方确认**；③ 大文件（FR-7 要求 >4GB）不适用，只能分片多文件上传并自建清单 → 结论：**>100MB 一律走自建** |
| 加密要求 | 只上传**密文**；分享密码与解密口令都不得经由 SECTL 传递 |

### 3.6 软件分发 / 自动更新

| 项 | 结论 |
|---|---|
| 可用性 | ✅ **完全可借力，且不需要登录、不需要 scope**（来源：`API/分发/软件分发.md`，访问级别「公开读取」） |
| 流程 | 启动时 `GET /api/software/latest-tag?projectSlug=SecRelay&channel=stable` → 与本地版本比 → `GET /api/software/download?...`（**必须允许跟随 302**） |
| 通道 | `stable`（`tag=latest` 永远指最新正式版）与 `prerelease`（仅在"预发布领先"时存在，否则 404）——正好对应 SecRelay 的 beta 通道 |
| 硬限制 | **STK 只保留最近 1–2 个版本**，历史 tag 会回落 GitHub（`fallback: true`）；多资产匹配返回 409 `ambiguous_package`，需补 `fileName`/`os`/`arch` |
| 前置 | 仓库必须已登记为软件分发项目；**登记方式需向账号系统维护方确认** |
| 风险与对策 | ① 第三方单点：必须保留 GitHub Release 直连与"手动下载"兜底，更新失败不得阻塞启动；② **分发渠道与完整性校验必须解耦**：无论从 STK 还是 GitHub 下载，都**必须校验自签名**（Ed25519 + 清单哈希），绝不因为"来自 SECTL 域名"就信任 |

### 3.7 桌面通知 vs 通知接口（**明确写死：不要拿它做"文字提示到桌面"**）

| 项 | 结论 |
|---|---|
| 通知接口是什么 | 一个**站内通知记录**的读写接口（send / list / read / read-all / delete），文档中**没有任何推送、长连接、Webhook、桌面投递**能力 |
| 谁能发给谁 | **普通用户只能给自己发**；只有管理员（`permission >= 10`）能向任意用户发送（来源：`通知接口.md` §权限说明） |
| 因此 | ❌ **FR-9「文字提示到电脑桌面」不能借它实现**——用户 A 无法向用户 B 发通知（会 `403 forbidden`），且它也没有送达桌面的机制。FR-9 必须走 SecRelay 自己的 `notify` 频道（对方在线直连）+ 离线消息后端（对方离线） |
| 它可以做什么 | ① 客户端**给自己**发（如"某台设备已连入"的心理提醒/跨端提示）；② 平台/管理员做运营公告与版本通知；③ 服务端用平台 token 给指定用户发（需管理员权限，**需向账号系统维护方确认**平台 token 是否享有该权限） |

### 3.8 统计 / 遥测

| 项 | 结论 |
|---|---|
| 可借力 | ✅ 全部上报端点**公开、无需认证**：`/api/stats/online`（心跳）、`/api/stats/version`（启动一次，按 `device_uuid` 去重）、`/api/stats/usage/increment`（累计，`delta` 1–10000）、`/api/fields/values`（最新值，字段须先建） |
| 关键坑 | ① `/api/stats/online` 的 `device_type` 必须命中枚举（含 `-web` 变体），**不能用 OAuth 的 `device_type` 混用**；② `usage/increment` 不传 `period` 时**按字段名兜底且不会进总档**；③ IP/地区**只由服务端解析**，私网地址（`10.x`/`192.168.x`/`127.x`）一律忽略；④ 限流 120/min、600/min，失败要静默忽略 |
| 结合 KPI | 「中继占比 <15%」等自研指标应走 **自己后端**，不要塞进账号系统统计（它按 `platform_id + field_key` 汇总，无设备维度反馈） |
| 隐私红线 | 不上报设备名、用户内容、对端标识、IP 之外的网络信息；公开端点意味着**任何人都能伪造上报**，所以在线数不等于真实用户数，不要据此做运营决策 |

### 3.9 不使用 `permission` 等级做功能分级

`userinfo.permission` **不用于 SecRelay 的任何功能开关**。原因很直接：普通用户的取值基本都是 `1`，
按它分级等于没有分级；而且它的完整档位语义不在公开文档里，依赖它是在依赖一个不稳定且无收益的字段。

- 需要"内测通道 / 实验特性"时，用**自己的配置开关**（本地配置，或自建后端的开关），不要借账号系统的等级字段。
- 需要"运营公告"时，走账号系统自己的公告位，不需要 SecRelay 参与判断。
- **安全边界永远只有本地信任列表与 E2EE**：任何时候都不因"等级高"而放宽加密、跳过配对或允许无提示采集。

## 4. 硬性实现约束（提炼自 `API/OAuth/客户端授权登录.md` §10）

### 4.1 必须遵守的九条

| # | 约束 | 做错的后果 |
|---|---|---|
| 1 | **原子落盘**：拿到刷新响应后先把**新的 access + refresh 一起**写入（临时文件 + `rename`，或 SQLite 事务），**再用**新 access token 发业务请求 | 中途崩溃 = 旧 token 已失效 + 新 token 丢失 = 会话死亡；只放内存则进程重启后必然 `refresh_token_reused` |
| 2 | **single-flight**：同一时刻只允许一个刷新在飞，其余等待其结果；多进程共享 token 时用**文件锁**或把刷新收敛到单一后台进程 | 并发刷新时一个成功轮换，另一个拿旧 token 再来 → `invalid_grant`；真正的盗用判定会**撤销整个令牌家族** |
| 3 | **错误分类**：只有 `400 invalid_grant` / `401 invalid_client` 是终态（清空 token、重新授权）；`429 rate_limited` 按 `retry_after_ms` 退避重试**同一次**；`503 temporarily_unavailable` 指数退避 + 抖动；网络超时先**重读本地 token**（可能已被别的刷新更新） | 拿旧 token 死循环 → 刷出大量 429、服务端噪声与撤销记录 |
| 4 | **时间常量**：access token 有效期以响应的 `expires_in` 为准（当前 **3600s**），到期前 **5 分钟**刷新；refresh token 自**首次授权**起固定 **180 天**，**轮换不延长**，满 180 天必须重新授权 | 用户被强制重新登录；或误以为"一直刷新就能永久在线" |
| 5 | `device_uuid` 必须是**标准 36 位 UUID**，同一实例刷新时**保持不变**；首次运行生成后持久化 | 设备识别错乱；`invalid_request` |
| 6 | 必须带**可读的 `User-Agent`**（如 `SecRelay-Desktop/0.1.0 (Windows)`） | 设备名显示为「未知设备」；服务端程序（`node`/`curl`）还会被判为未知类型 |
| 7 | **绝不上报 IP**：服务端按 `x-appwrite-client-ip` → `CF-Connecting-IP`/`X-Real-IP`/`X-Forwarded-For` 解析真实公网 IP，传了 `ip_address` 也被忽略 | 徒劳 |
| 8 | 心跳 `/api/oauth/heartbeat` 每 **5 分钟**一次；`devices_updated: 0` 不是错误；平台设备页在线窗口 **30 分钟** | 设备页显示离线 |
| 9 | 业务请求收到 `401 invalid_token` 时**看 `error_description`**：`Access token has expired` → 刷新一次后重试原请求；`Access token has been revoked` → 直接重新授权（刷新不会成功） | 白刷一轮 |

### 4.2 刷新状态机（Rust 视角）

```
需要 access token
  ├─ 本地未过期(>5min)            → 直接用
  └─ 即将过期
       ├─ 已有 in-flight 刷新      → 等它（single-flight / tokio::sync::Mutex + OnceCell）
       ├─ 跨进程持有文件锁失败      → 等待/重读本地 token（可能已被守护进程刷新）
       └─ 发起 POST /api/oauth/refresh
            ├─ 200            → 事务写盘(access+refresh+expires_at) → 返回
            ├─ 429/503        → 退避后重试同一请求（限次）
            ├─ 400 invalid_grant / 401 invalid_client → 终态：清 token、进入"未登录"
            └─ 网络错误/超时   → 重读本地 token；无更新则退避重试一次，仍失败→未登录
```

> §10 还写明了**60 秒宽限窗口**：轮换后短时间内重复提交旧 token 会返回 `invalid_grant` 但**不撤销家族**，客户端手上的新 token 仍然有效。这是唯一被允许的"重试"情形——它恰恰说明**不能**把 `invalid_grant` 当成"再试一次就会好"，而应把它当作终态并保证本地已持久化新 token。

### 4.3 本地开发必踩的坑（务必写进 README）

| 坑 | 说明 |
|---|---|
| **内网 IP 直接 `forbidden`** | 换 token 与刷新都会解析客户端真实公网 IP；若解析出**内网/保留地址**（容器地址、`10.x`、`192.168.x`）**直接返回 `403 forbidden`**（来源：`客户端授权登录.md` §2/§3 错误表）。**本机/容器里开发调试时会稳定失败** |
| 应对 | 用真实公网出口（家庭宽带/手机热点）、经公网出口的代理、或在测试环境走一台有公网 IP 的机器；**不要**尝试伪造 `X-Forwarded-For`（受信代理头顺序由服务端决定，且属于规避行为） |
| 环回地址规则 | 只有 `localhost`、`127.0.0.0/8`、`[::1]` 的 HTTP(S) 回调可动态端口；`*` 只允许写在端口位；**自定义 Scheme 与环回回调强制 PKCE(S256)** |
| 统计接口的私网 IP | 被忽略并记为"未知/空"，地区统计全错 —— 不要据此判断"上报成功即地区正确" |

## 5. 密码学红线

| 项 | 规则 |
|---|---|
| **永不上云**（本地密钥库 / 内存） | 设备私钥（Ed25519 / X25519）、双棘轮根密钥·链密钥·消息密钥、预共享密钥、配对码与 SIX 位码、SAS 比对值、明文消息与明文文件内容 |
| **可上云（白名单）** | 设备**公钥**、设备型号/平台（非主机名）、协议与能力版本、**密文**（离线消息体、文件内容）、用户自选的展示名 |
| **禁止** | 把 SECTL 的 token 当作"设备身份"；把"账号内的设备列表"当作信任依据；用 `device_uuid`（OAuth 的）替代 SecRelay 设备指纹；把解密口令/分享密码经由 SECTL 传递 |
| 零知识如何仍成立 | ① OAuth 只交换**身份**，密钥材料从不经过 SECTL；② KV/云存储只放密文或公开信息；③ 中继不验证账号、只转发密文（§2.3-1）；④ 首次配对必须带外（禁止纯在线配对）；⑤ 离线消息用双棘轮而非"设备公钥加密存起来"，使**服务器被拖库也不能解历史与未来**（`需求分析.md` §6.3 修正 3） |
| 唯一无法消除的泄露 | **元数据**：谁在何时登录、几台设备、地区、云文件的大小/时间/数量、分享链接访问记录。接入账号系统后这部分必然由 SECTL 掌握，必须写进隐私政策 |

## 6. 威胁模型

### 6.1 账号被盗（凭据/OAuth 令牌被他人取得）

| 会损失 | 不会损失 |
|---|---|
| 云存储与 KV 里的**密文**（可读不可解）、设备列表元数据（设备名、公钥、最后在线）→ 可用于指纹与社工；可用该账号上传垃圾文件耗配额、删分享链接、删除通知；攻击者可用该账号**新授权一台设备**，让"未知设备"出现在用户设备页 | **设备私钥与会话密钥**（在 OS 密钥库，不在服务器）；历史与未来消息明文；文件明文；屏幕/摄像头内容；中继流量无法解密；**无法与任何设备建立会话**——配对需带外二维码 + 六位码 + SAS，账号被盗不足以通过配对 |
| 缓解 | 密钥库存储；设备列表 UI 显著提示新设备与异常登录；引导用户使用 SECTL 侧"退出全部登录"（`/api/oauth/logout-all` 仅 Web 会话可发起，**客户端是否可吊销其它设备令牌需向账号系统维护方确认**）；关键操作（新增信任设备）强制带外确认 |

### 6.2 SECTL-auth 被拖库

| 会损失 | 不会损失 |
|---|---|
| 用户资料（邮箱、姓名、GitHub、生日、地区、标签、QQ 绑定）、设备信息（`device_uuid`、主板 ID、IP/地区、在线记录）、云文件与 KV 的**密文与元数据**、分享链接与访问统计、统计遥测数据 | 任何消息/文件**明文**（只要守住 §5 白名单）；设备私钥与双棘轮密钥（不在服务器）；而且文档说明服务端**只保存令牌哈希**（`客户端授权登录.md` §10），因此拖库**不能直接重放 refresh token** |
| 无法避免 | 元数据（通信关系、设备数量、地区）与"哪些用户在用 SecRelay"这一类**关联信息** —— 这是接入第三方账号系统的固有代价，必须在隐私说明里承认 |

### 6.3 SECTL-auth 服务不可用

| 阶段 | 行为 |
|---|---|
| access token 仍有效（≤1h） | 云存储/KV/资料全部照常 |
| 刷新失败（503/429/网络） | 按 §4.1-3 退避重试；期间本地已有 access token 仍可用；`429` 时不要打爆 |
| 长期不可用 / refresh 过期 | 云存储、KV、分享链接、通知、资料、**软件分发与统计**全部降级；桌面/移动端回到"未登录"状态 |
| **核心功能** | ✅ **全部不受影响**：设备密钥、配对、P2P 打洞、中继（不验证账号）、屏幕/摄像头/投屏、文件 P2P 直传、在线文字与语音、自建离线消息后端 |
| 结论 | **账号系统挂了，SecRelay 依然能用**，只是退化为"无账号模式"：不能跨账号看身份、不能云端中转与自同步、自动更新需回退到 GitHub/手动。**这是 §2 分层设计的验收标准：任何把账号放进核心路径的实现都算设计违约。** |

## 7. Rust 实现建议

| 关注点 | 建议 | 理由 |
|---|---|---|
| OAuth 协议 | `oauth2`（5.x）+ `reqwest`（rustls-tls）；或直接用 `reqwest` 手写 | `oauth2` 的 `AuthorizationCode`/`PkceCodeChallenge(S256)` 覆盖 authorize/exchange；但**刷新轮换 + 错误分类 + 原子落盘**语义与库默认行为不一致，刷新务必自己实现（库的自动刷新没有 single-flight 与先落盘约束） |
| HTTP | `reqwest` + `rustls`，显式设置 `User-Agent`，禁用重定向（分发下载除外，需跟随 302） | 上报头正确则设备名可读；`forbidden`/`invalid_grant` 判定依赖精确状态码 |
| 并发 | `tokio` + `tokio::sync::Mutex`/`OnceCell` 做进程内 single-flight；`fd-lock`/`fs2` 做跨进程文件锁 | §4.1-2 |
| 原子写 | `tempfile::NamedTempFile::persist`（rename）或 `rusqlite` 事务 | §4.1-1 |
| Token 存储 | **OS 密钥库**：`keyring`（Windows **Credential Manager** / macOS **Keychain** / Linux **Secret Service**(gnome-keyring/KWallet)）；Android 走 **Keystore**（JNI/平台层）；Web 端不落盘 refresh token | 见下 |
| 敏感内存 | `secrecy` + `zeroize` | 减少 core dump/日志泄密 |
| 设备标识 | `uuid`（v4）生成 OAuth `device_uuid`；`random_uuid` 落盘到配置目录（非机密，但必须稳定） | §4.1-5 |
| 打开浏览器 | `open`/`webbrowser` crate 拉起系统浏览器（不要 WebView） | 环回回调 + PKCE 更安全 |
| 退避 | `backoff` 或自写（429 用 `retry_after_ms`，503 指数+抖动） | §4.1-3 |

**为什么不能只存明文文件**：

1. refresh token 是 **180 天**有效的长期凭据，泄了就等于把用户的云端读写能力交出去（令牌文件常被云盘/备份工具同步出去，`~/.config` 明文极易被同一用户下的任意进程读取，也没有 per-app ACL）。
2. 明文文件无法区分"哪个应用可以读"，密钥库能（macOS Keychain ACL、Linux Secret Service 会话解锁、Android Keystore 硬件保护）。
3. 明文文件在多进程下更容易出现"读到旧 token 再刷新"的竞态（§4.1-2），而密钥库本身**不提供锁** —— 所以：**token 放密钥库，刷新互斥仍要靠文件锁或单一守护进程**（两者都要做）。
4. 兜底：密钥库不可用（如无 Secret Service 的 Linux 无头环境）时应降级为**加密文件 + 明确告知用户**，而不是静默明文；并允许用户选择"每次都重新登录"。

| 7 | KV 的 1000 键 / 64KB 限额是**按 (用户, 平台)** 计数吗？超限是拒绝还是淘汰？ | 决定分片策略 |
| 8 | 云存储**默认配额**是多少、如何申请上调？ | 决定文件中转能否作为可用功能 |
| 9 | 分享链接的短码是否**不可枚举**？是否支持除密码外的访问控制（如仅登录用户可访问）？ | 决定分享链接能否承载密文文件 |
| 10 | 是否有**撤销/轮换分享链接**与访问日志能力（文档提到 `view_count`/`download_count`）？ | 泄密后的处置 |
| 11 | 限流是否按 `client_id` 分桶？多设备高并发刷新是否需要加白名单？ | 大规模用户下的刷新风暴 |
| 12 | 自定义 Scheme 的注册格式：`secrelay://oauth/callback` 与反向域名形式 `cn.sectl.secrelay:/oauth2redirect` 哪种被接受？ | 决定 Android/桌面回调 |
| 13 | 是否允许把云存储/KV 用于**端到端加密的密文暂存与文件中转**（服务条款/政策层面，非技术层面）？ | 避免用途违规导致封停 |
| 14 | 平台后端云服务（`platform-storage`）是否对 SecRelay 开放？delegated token / offline grant 的申请与有效期？ | 若开放，SecRelay 自己的后端可在不落 SECTL bucket 的前提下记用户配额 |

> 注：`userinfo.permission` 等级字段**不在待确认清单里，也不需要确认** —— SecRelay 不拿它做任何判断（见 §3.9）。

---

## 9. 一句话总结

**把 SECTL-auth 当成"身份 + 自同步 + 分发 + 遥测"四件事的供应商，不要当成消息系统**：登录、资料、设备清单同步、≤100MB 文件中转、自动更新与统计可以借力；**用户与用户之间的任何投递（离线消息、桌面提示、好友关系）一律借不上，必须自建**；实现的成败取决于三件事——**核心路径不依赖账号**、**密钥永不触云**、**刷新令牌的原子落盘 + single-flight + 错误分类**做对。
